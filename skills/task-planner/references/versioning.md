# 版本号决策规则

本文档定义 docs/tasks/ 下版本号的确定逻辑，包括 major/minor 判定和内容过多时的拆分策略。

## 版本号格式

```
v<major>.<minor>
```

示例：`v1.0`, `v1.3`, `v2.0`

## 决策优先级

版本号按以下优先级从高到低确定：

### 1. 用户显式指定

用户通过参数指定版本号时直接采用：
```
/ai:discuss summarize <topic> --version 2.0
```

### 2. Requirement-analyzer 建议

调用 requirement-analyzer 评估后，基于以下规则判定 major/minor：

| 条件 | 版本类型 | 示例 | 说明 |
|------|---------|------|------|
| 新增独立功能模块 | minor (+0.1) | v1.0 → v1.1 | 不影响现有功能 |
| 现有功能增强/优化 | minor (+0.1) | v1.1 → v1.2 | 向后兼容的改进 |
| Bug 修复/小调整 | minor (+0.1) | v1.2 → v1.3 | 修正性变更 |
| 架构重构/破坏性变更 | major (+1.0) | v1.3 → v2.0 | 不向后兼容 |
| 全新项目方向 | major (+1.0) | v2.0 → v3.0 | 战略性调整 |
| 跨模块依赖重组 | major (+1.0) | v1.0 → v2.0 | 影响多个子系统 |

**判定因子（由 requirement-analyzer 评估）：**
- 技术复杂度 ≥ 7 → 倾向 major
- 涉及破坏性变更（接口删除/重命名/行为改变）→ major
- 影响 ≥ 3 个独立模块 → 倾向 major
- 其他 → minor

### 3. 自动递增

扫描目标项目 `docs/tasks/` 下已有 `v*` 目录，取最大版本号：
- 如存在 `v1.0/`, `v1.1/` → 新版本为 `v1.2`
- 如存在 `v2.0/` → 新版本为 `v2.1`

### 4. 首次使用

目标项目 `docs/tasks/` 下无任何版本目录时，默认 `v1.0`。

## 拆分策略

当 requirement-analyzer 评估结果满足**以下任一条件**时，task-planner 应主动建议拆分：

### 拆分触发条件

| 条件 | 阈值 | 说明 |
|------|------|------|
| 时间估算 | > 21 天 | 超出单 Sprint 限制 |
| 复杂度评分 | > 8/10 | 技术风险过高 |
| Sprint 数量 | > 4 | 管理复杂度过高 |
| 独立功能模块 | > 8 个 | 范围过大 |
| 依赖外部系统 | > 3 个 | 集成风险高 |

### 拆分方案模板

当检测到需要拆分时，生成以下建议并请求用户确认：

```markdown
## 拆分建议

原始需求「{{NAME}}」评估为过大，建议拆分为多个版本阶段：

| 版本 | 名称 | 范围 | 预估 Sprint |
|------|------|------|------------|
| v{{BASE}}.0 | {{NAME}} - 基础 | 核心功能模块 | 2 |
| v{{BASE}}.1 | {{NAME}} - 增强 | 次要功能模块 | 1-2 |
| v{{BASE}}.2 | {{NAME}} - 完善 | 优化和打磨 | 1 |

拆分原则：
1. 每个版本可独立交付和验证
2. 核心功能放在第一个版本
3. 版本间保持向后兼容
4. 每个版本 Sprint 数 ≤ 3
```

### 拆分优先级

拆分时按以下优先级分配功能到各版本：

1. **v<X>.0 (核心)** — Must Have 功能，无外部依赖，可独立验证
2. **v<X>.1 (增强)** — Should Have 功能，依赖核心版本
3. **v<X>.2 (完善)** — Nice to Have 功能，优化和文档

用户确认拆分方案后，task-planner 为每个版本分别生成 plan.md 和 task.md。

## 版本目录结构

```
docs/tasks/
├── README.md               # 使用指南和版本索引
├── v1.0/                   # 已完成版本
│   ├── plan.md
│   ├── task.md
│   ├── knowledge.md        # 归档时生成
│   └── ARCHIVED.md         # 归档时生成
├── v2.0/                   # 进行中版本
│   ├── plan.md
│   ├── task.md
│   └── state.json          # OODA 状态（可选）
└── v2.1/                   # 待开始版本
    ├── plan.md
    └── task.md
```

## 版本状态检查

使用脚本检查所有版本的状态：

```bash
bash skills/task-planner/scripts/check-version-status.sh
```

输出示例：
```
📋 版本状态概览
v1.0  ✅ archived  (9/9 tasks, 100%)
v2.0  🔄 in_progress  (3/8 tasks, 37%)
v2.1  ⏳ pending  (0/5 tasks, 0%)
```
